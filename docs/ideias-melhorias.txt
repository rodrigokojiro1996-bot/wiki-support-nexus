4. MIGRACOES NUMERADAS DO BANCO          (prioridade 3)
-------------------------------------------------------------
Por que: CREATE IF NOT EXISTS nao altera tabela existente, e o
"try: ALTER TABLE ... except: pass" no seed.py esconde qualquer outro erro.

Como:
- backend/app/migrations/001_inicial.sql (schema atual sem a coluna fontes),
  002_manuais_fontes.sql (ALTER TABLE manuais ADD COLUMN fontes ...).
- Tabela schema_version; db.py aplica em ordem so as que faltam, cada uma
  numa transacao.
- Banco existente sem schema_version mas com a coluna fontes -> marcar versao 2.
- Remover o try/except do seed.py.

Como conferir: banco novo e copia de um banco atual terminam com o mesmo
".schema".

-------------------------------------------------------------
6. MODO DE PRODUCAO COM UM SO PROCESSO   (prioridade 3)
-------------------------------------------------------------
Por que: hoje so existe modo de desenvolvimento (--reload + vite dev). O PDF
abre o frontend em localhost:5173, entao sem o vite rodando nao ha PDF.

Como:
- "npm run build" gera frontend/dist; o FastAPI serve dist/ como StaticFiles
  na raiz (com fallback para index.html por causa do React Router).
- NEXUS_FRONTEND passa a apontar para o proprio backend (ex.: 127.0.0.1:8010).
- GET /api/saude: SELECT 1 no SQLite + versao -> {"ok": true, "versao": "0.1.0"}.
- iniciar.ps1 continua para desenvolvimento; criar iniciar-producao.ps1
  (build + uvicorn sem --reload).
- Depois: Dockerfile com HEALTHCHECK em /api/saude, se for para um servidor.
  Atencao: o PDF usa Edge (channel msedge); no Linux/Docker trocar
  NEXUS_PDF_CANAL para chromium e instalar com "playwright install chromium".

Como conferir: com o vite DESLIGADO, abrir a interface pela 8010 e baixar um PDF.

9. DESEMPENHO DO DIAGRAMA COM BANCO REAL (prioridade 6)
-------------------------------------------------------------
Por que: com 30 tabelas nao aparece, mas um ERP real tem centenas.
- /diagrama faz 2 consultas POR tabela incluida (tabelas + colunas): trocar por
  uma consulta com "WHERE tabela IN (...)" e agrupar em Python.
- O calculo de "conexoes" para o corte em 40 percorre todas as relacoes para
  cada tabela: pre-calcular um indice {tabela: [relacoes]} uma vez.
- Carregar SQL_RELACOES uma vez por requisicao (hoje e reaproveitado, ok) e
  considerar cache por banco invalidado no seed.
- Teste de desempenho: catalogo sintetico com 500 tabelas / 2000 relacoes,
  /diagrama deve responder em menos de 500 ms.
